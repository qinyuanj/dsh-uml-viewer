# 0016 把项目根之外的路径复制进每个 Windows 副本

**Status**: accepted

## 背景

第一个使用方是 qinyuanj/kacha#102 的质量门禁：它按包运行质量工具
（`mutator --root client` 只变异包自身的源码），而这个包的单元测试读的是仓库根、
不在包内的数据（`import policy from "../../../contracts/board-policy.json"`），
所以测试需要一个离开项目根的路径。

Linux 本来就没问题：namespace view 是挂在**项目根上**的 overlayfs，视图里的 `..`
直接到真实父目录，旁边的 `contracts/` 本来就可读，基线不需要任何开关就能通过。

Windows 的 copy 隔离把项目根复制进私有 scratch slot（`<slot>/project`），覆盖率、
基线和每个变异体都在这份副本里跑。副本没有兄弟目录，`../contracts` 解析不到，
于是**未变异的基线就先失败**，一个变异体都不会跑。这样的包在 Windows 上没有任何
可用的变异结果，质量门禁什么都报不出来。

## 决定

`mutator` 新增 `--copy <path>`，可重复：

- `path` 相对 `--root`，且必须离开它：**项目根内**的路径是用法错误（副本本来就有
  它）；绝对路径、多个前导 `..`、解析回项目根内、路径不存在，同样是用法错误。
- 恰好允许一个前导 `..`，因为这是副本能兑现的：Windows 副本是 `<slot>/project`，
  `..` 就是 slot，路径放到 `<slot>/<规范化后的相对路径>`。规范化后只剩普通组件，
  所以复制永远不会写到本次调用的 scratch root 之外。
- 顺序不敏感，且同一位置声明两次是**一次**外部复制，不是错误：
  `../contracts`、`../docs/release`、`../server/Cargo.toml` 与其中任一重复的三条
  是同一个调用。目录按树复制、单文件按文件复制，所以单个依赖文件不需要在项目里先
  建父目录：`<slot>/server/Cargo.toml` 的 `server/` 由这次复制创建。
- Windows 在**每个命令之前**从项目根旁的同一相对位置重新放置：slot 先被清空，因此
  变异体对 `..` 的写入既到不了下一个命令，也到不了真实树，真实树永远不被写。副本活
  在 scratch root 内，随它一起删除；放置失败就让该命令失败并写出路径
  （`Copy isolation cannot place <path> beside the copy: …`），绝不留下一份悄悄缺依赖
  的副本。放置失败不是测试结果，所以它退 **1**（isolation unavailable），与其它隔离
  拒绝同一退出码，绝不是「测试套件失败」的 2。
- slot 自己的条目不是可选位置：`project`、`home`、`temp`、`appdata`、`output`、
  `mutation`（大小写不敏感）作为规范化后的首组件时是用法错误。副本把项目放在
  `project`，把 HOME/TEMP/APPDATA 重定向到 `home`/`temp`/`appdata`，并在每条命令前重建
  `output` 与 `mutation`：放在那里的外部路径会在命令读到它之前被删掉，或者把外部
  目录合并到项目副本上覆盖源码。判定只看规范化后的首组件，与路径是否存在无关。
- Linux 接受并校验同一套参数，但不复制：它的视图本来就看得见真实父目录。于是两个
  平台拒绝的是同一批错误参数，而不是「只在 Windows 上失败的拼写错误」。
- 一套外部路径属于**一次调用**，只登记一次，所以这次调用创建的每个视图——覆盖率、
  基线、变异体——看到的都是同一批路径。
- 错误参数走现有的用法错误路径：错误信息 + help 文本，退出 1，发生在平台判定与任何
  命令之前。

## 被否决的方案

- **复制项目根的整个父目录，或整个仓库**：副本总是自足，但会把项目再复制进它自己的
  父目录（上界是仓库根、home 目录），而且代价落在每条命令上。否决。
- **接受任意路径（包括绝对路径），用合成名放置**：绝对依赖确实简单，但真正会坏的是
  相对 `..` 依赖（被固定版本的源码就是相对 import），合成名会改变命令的解析方式。
  否决：放置位置必须保持真实相对路径，未改动的测试才能照常工作。
- **在 `uml-quality.json` 里声明，而不是 CLI 选项**：能按项目记录一次依赖，但依赖属于
  调用而不属于项目：同一个清单会用不同的包根与不同的测试命令，不经过 dispatcher 的
  调用（直接 `uml-viewer mutate`）还得另做一套传递。否决。
- **只在 Windows 接受该选项**：Linux 上脚本一带上它就失败，每个调用方都要按平台分叉。
  否决：选项在接受它的平台上无意义，而无意义恰恰是因为依赖本来就可见。
- **让 copy 隔离自动放置兄弟路径**（扫描 import，或复制测试打开过的每个 `..` 目标）：
  副本会去猜命令读什么，结果还依赖运行顺序。否决：调用方声明它需要什么，没声明的
  路径继续缺失，与原版一致。

## 后果

- mutate 的 help 文本不再与被固定版本的 Python 原版逐字节相同：它多了一个只属于本
  移植的选项。`fixtures/mutate/help.txt` 是这个移植 help 的来源，测试比对它。
- 调用方为每条声明路径、每条命令多付一次树复制。`--copy` 只用于命令真正读的东西，
  不是整个 checkout 的父目录。
- dispatcher（`uml-viewer quality mutate`）必须知道 `--copy` 取一个值，否则那个路径
  会被当成 target 名；它已进入 `quality-dispatch` 的取值选项表。
- 基线仍在真实项目树里跑，那里兄弟路径本来就可见，所以 `--copy` 不需要基线侧行为：
  选项在两个平台上都在任何命令之前校验，只影响副本。
- 副本是约定，不是沙箱（[ADR 0010](0010-native-windows-delivery-platform.md)）。`--copy` 不扩大这个断言：项目外的绝对路径对命令
  依然可见，而通过被复制路径的写入只改该命令的副本，不改真实树。
- 测试：解析器有一张参数矩阵（`isolation_outside_tests.rs`），含六个保留名及其嵌套
  路径、大小写变体；Windows 集成用例在**不带**开关时基线失败，在**带**两条目录加一个
  文件时杀死全部变异体，并证明 `../output` 在真实仓库里被拒、放置失败退 1；Linux 用例
  带开关运行成功、看到真实父目录，并且带与不带发布逐字节相同的快照。
